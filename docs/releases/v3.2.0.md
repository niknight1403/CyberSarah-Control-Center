# Release v3.2.0 — Autonomes MCP-Governance-System

**Datum:** 11.11.2026
**Vorherige Version:** 3.1.1
**Umfang:** Sprints 1–10 der MCP-Mission (Registry, Vault, Supervisor, Governance, Agenten, Team, Lauf, Ausführung, Freigaben)

## Was dieses Release liefert

Das Control Center kann MCP-Server verwalten, ihre Werkzeuge semantisch verstehen, Agenten
dagegen prüfen, Aufgaben delegieren, Läufe mit harten Limits ausführen, echte Aufrufe über
eine geprüfte Brücke machen und riskante Aufrufe nur mit menschlicher Freigabe zulassen.

| Modul | Endpunkte | Kern |
|---|---|---|
| Multi-Server-Registry | `mcp.servers.*` | Tabelle `mcp_servers`, Health-Score, Tool-Cache, Least-Privilege bei Registrierung |
| Credential Vault | `mcp.credentials.*` | AES-256-GCM, Schlüssel außerhalb der DB, Rotation |
| Connection Supervisor | `mcp.supervisor.*` | Circuit Breaker, Backoff, Ratenlimits |
| Governance | `mcp.governance.*` | Semantische Tool-Suche, Risikoklassen, Policy-Gate, Argument-Sanitizing |
| Agent Factory | `mcp.agents.*` | Agenten als prüfbare Spezifikation gegen den echten Katalog |
| Team-Orchestrierung | `mcp.team.*` | Zerlegung, Delegation, Budgetaufteilung, Schleifenerkennung |
| Run-Engine | `mcp.runs.*` | Step-Loop, Budget-/Schritt-/Zeitlimits, Abbruch, Pause |
| Execution Bridge | `mcp.execution.*` | Werkzeugwahl nur aus Grants, Policy vor Netzwerk, Audit ohne Werte |
| Freigaben | `mcp.toolApprovals.*` | Queue, Ablauf, Vier-Augen, Bindung an den konkreten Aufruf |

## Betriebszustand (wichtig)

- **Live-Werkzeugaufrufe sind standardmäßig AUS.** Sie brauchen `MCP_LIVE_EXECUTION=1`.
  Ohne diese Variable bleibt der `refusingExecutor` aktiv und jeder Lauf endet mit
  `execution_disabled`. Es wird kein Erfolg vorgetäuscht.
- **Freigaben wirken nur mit Aufruf von `mcp.toolApprovals.sweep`.** Es gibt keinen Cron;
  abgelaufene Anfragen bleiben sonst offen stehen.
- **Zwei Tore für riskante Aufrufe:** Lauf fortsetzen (`mcp.runs.approve`) und Werkzeug
  freigeben (`mcp.toolApprovals.decide`) sind absichtlich entkoppelt.
- **Prüfer sind Namen, keine Identitäten.** Das Vier-Augen-Prinzip ist eine erzwungene
  Regel, aber ohne Auth-Bindung keine kryptografische Garantie.

## Bekannte Grenzen

1. Kein Ende-zu-Ende-Lauf gegen einen echten Fremd-MCP-Server; alle Aufrufpfade sind mit
   Fakes getestet.
2. Kein Hintergrundläufer: Läufe werden über `step`/`advance` angestoßen, nicht von einem
   Worker weitergezogen.
3. Kosten sind geschätzt (5 Cent je Aufruf), nicht gemessen.
4. Keine Benachrichtigungen für offene Freigaben.
5. Audit ist per API unveränderlich, aber nicht manipulationssicher.
6. Ein Werkzeug pro Aufgabe, kein Multi-Tool-Schritt.
